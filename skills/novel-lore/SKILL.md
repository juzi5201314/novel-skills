# 交互式设定

**自动化增强**：本技能按 novel-core/AUTOMATION.md 的机制运行。新建或修改设定后自动同步 glossary.md、AGENTS.md（新硬规则），并检查与正文冲突。

目录、文件格式、模板遵循 novel-core 技能，开始前先读它。分类以 AGENTS.md"设定分类"注册表为准，各分类的字段模板在该目录的 `_schema.md`。

## 流程

### 1. 确定要做什么

从用户的话里判断：新建还是修改、什么类型、一个还是一批。说得很模糊（“完善一下世界观”）时，先读 AGENTS.md、lore/ 目录和 outline/synopsis.md，找出缺口，把缺口列成多选题让用户挑（“力量体系缺少寿元设定”“主角所在的宗门还没有决策层”“主角的家人还没有人设”）。

**实体该放进哪个分类**：按 AGENTS.md"设定分类"注册表归属；不属于任何已有分类时，先问用户要不要加新分类（`novel.py category add`），不要硬塞进现有目录，也不要默认它该叫"门派"——用户叫它什么就是什么。

### 2. 先读已有设定

动笔前读：AGENTS.md 的硬规则和核心设定、「规则」节场景表里的 lore 规则文件（若有）、lore/glossary.md、相关类型目录下的已有文件、和新实体有关系的实体文件。改已有实体时，用 `novel.py find --entity <名>` 查正文里已经写过的内容：正文写过的事实是“已发生”，设定不能改得和它矛盾，除非用户明确要改正文（那属于 novel-chapter 的改稿）。

### 3. 交互提问

用提问工具（omp 的 `ask`、Claude Code 的 `AskUserQuestion` 等）收集关键决策。互不依赖的问题合并到一次调用，最多 4 个，依赖前面答案的放下一轮。

- 选项要具体，各自通向不同的故事可能。坏选项：“性格开朗/性格内向”。好选项：“表面圆滑的情报贩子，记仇，账本上记着每个欠他人情的人”。
- 每个问题标推荐项，并在描述里说明这个选择会给剧情带来什么（带来什么走向、和谁形成对照、能埋什么伏笔）。
- 只问决定性的问题，次要细节你直接补上，最后让用户一并过目。
- 用户说“你定”，就按推荐走并告知。

各类型的关键决策（示例表，用户自定义的分类参照最近一行类比，字段以该目录 `_schema.md` 为准）：

| 类型 | 关键决策 |
|---|---|
| 角色 | 剧情功能（盟友/对手/导师/镜像/工具人反转）、核心欲望与缺陷、与主角的关系、秘密、说话方式 |
| 组织/势力 | 定位与实力档次、决策方式和内部派系、想要什么、对主角的初始态度、隐藏的底牌 |
| 地点 | 剧情用途（打斗场/据点/秘境/过场）、一个标志性的感官特征、规则与危险、谁控制它 |
| 物品 | 能力、限制与代价、来历、谁在找它 |
| 体系类 | 层级划分、达成条件、资源与代价、上限、越级/例外的可能性 |
| 历史 | 哪段历史会影响当前剧情、官方说法与真相的差别 |
| 伏笔/暗线 | 真相、埋设方式、读者应该在什么时候起疑、回收时机和方式、回收前的约束 |

### 4. 一致性检查

写入前逐条核对，发现冲突就告诉用户并给出解决方案让他选：

- 重名：glossary 里是否已有同名或近似名（同音、只差一个字）。
- 体系设定：能力、层级是否在本书体系类设定（`_schema.md` 中 `base: world` 的分类目录）定义的范围内；越级是否有合理代价。
- 时间线：年龄、辈分、历史事件的先后是否和 memory/timeline.md、体系类设定吻合。
- 正文：已发生的事实不能被推翻。
- 硬规则：不违反 AGENTS.md 里的任何一条。
- 伏笔：不和 memory/threads.md 里已有的真相打架。

### 5. 写入

- 按所属分类目录的 `_schema.md` 建文件，文件名用 glossary 中的标准写法；没有 `_schema.md` 就用通用模板 `entity.md`。用不上的小节删掉。
- `aliases` 写全称号、外号、敬称和别人对他的称呼。
- 关系是双向的：给 A 写了“与 B 是死敌”，也要在 B 的文件里补上。
- 新专名登记到 lore/glossary.md。
- 设定里的“秘密/隐藏设定”同步到 memory/threads.md 开新条目，写清“不可违反”约束。
- 动态状态（境界、所在、持有物）写进 memory/state.md，不写在 lore 里。
- 如果这个设定改变了全书级规则（如修改力量体系），同步 AGENTS.md 的“核心设定速查”或“硬规则”。

### 6. 汇报

列出新建/修改的文件，并点出两三处“这个设定可以怎么用”的剧情建议（例如“他的账本可以在第二卷成为主角要挟长老的筹码”）。不要长篇复述设定内容，用户可以自己打开文件看。

## 批量创建

用户要一批（“给青云宗设计 5 个长老”）时：

1. 先给一张表：每行一个实体，列出名字、一句话人设、剧情功能、与已有角色的关系。确保这一批内部有差异和层次，不要 5 个都是严肃的老头。
2. 让用户勾选保留哪些、改哪些（多选题）。
3. 确认后逐个按模板写入，再统一更新 glossary 和关联实体。

## 伏笔与暗线设计

暗线是全书级的隐藏设定，正文里只能露出痕迹。设计时：

1. 写清真相（只给作者看）。
2. 设计 3–5 个埋设点：在什么章节、以什么看起来无关的形式出现。
3. 定回收方式和大致章节。
4. 写“不可违反”约束：回收前哪些话不能说、哪些角色不能知道、哪些能力不能用。novel-review 会按这些约束审稿。
5. 登记到 memory/threads.md；相关实体文件的“秘密”小节注明编号。

## 设定图

- 用户要图时，先写一段绘图提示词，放进实体文件的“设定图”小节。提示词结构：主体 + 外貌特征（来自设定文件，保持一致）+ 服饰道具 + 姿态表情 + 场景 + 画风 + 构图。中英文各一版，英文版方便多数绘图模型使用。
- 当前环境有图像生成工具时，可以直接生成，存到 `lore/images/{实体名}-{用途}.png` 并在实体文件里引用。
- 用户提供了图片：复制到 `lore/images/` 按规则命名，在实体文件里引用；读一下图片内容，把设定文件里和图片不一致的外貌描述指出来，问用户以哪个为准。
- 地图：在地点文件里写清方位和距离关系，就能保证正文里的路程前后一致；需要画图时，提示词里列出所有地名和相对方位。
