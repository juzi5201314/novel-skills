# 章节创作

**自动化增强**：本技能按 novel-core/AUTOMATION.md 的机制运行，用户只说意图，所有文件操作、检查、同步由 agent 自动完成。

本技能处理从空白到成章的全流程。必读：novel-core 的正文格式与「创作主权」、novel-craft 的写作指导。

## 模式选择

创建新章（含番外）先确认模式，除用户措辞已明确指定外都问一次：

**明确指定（不问，直接走对应模式）**：
- 互动：「互动写」「陪我写」「一起写」「边写边选」「一段段来」「像游戏一样」等
- 快速：「快速写」「直接写」「自动写」「写完它」「一口气写」等

**未指定（"写第 N 章""续写""写个番外"等）**：用提问工具问一次——

> 这章怎么写？
> A) 快速模式：我一口气写完整章，你只管骨架审核和定稿
> B) 互动模式：我写一段你选走向，像剧情游戏一样推进

说"以后都按 X 写"就把该默认写进 AGENTS.md 硬规则或 rules/*.md（机制见 novel-core「规则文件」），之后不再问。

改稿、补写、查看骨架等已有章操作不涉及模式，不用问。

## 快速模式（一句话）

用户指定快速（"快速写""直接写"等）或模式选择时选了快速，用这个。给出一句两句的情节设想就能补全章纲——补出来的部分是自主生成不是定论，按下面"补全章纲"一节标「拟」请用户审核。

### 流程

#### 0. 开始前自动检查

Agent 自动（不展示命令，只展示结果摘要）：
1. 运行 `novel.py validate` 检查项目完整性
2. 检测未同步章节（扫描 chapters/ 实际最新 vs AGENTS.md 记录）→ 自动补同步
3. 检查 AGENTS.md 长度 → 超过 150 行自动归档历史规则到 lore/archive/

用户看到："检测到第 4 章未同步，已补同步 ✓"

#### 1. 读取上下文

AGENTS.md（已注入）→ 「规则」节场景表里的 writing 规则文件（若有）→ 本卷卷纲 → 是否已有章纲（有就读、没有就生成）→ memory/state.md + threads.md（"进行中"条目）→ 最近 3 章摘要 → 上一章末尾（约 1500 字）→ 本章出场实体的 lore 文件。

不要通读全书或所有 lore。

#### 2. 补全章纲

若章纲已存在、用户的一句话和章纲的大意相符，用现成纲；若是新描述或章纲缺，根据用户的想法和上下文生成骨架（目标、场景拆分、伏笔操作）。

骨架尽管自主生成：凡不是用户亲口说的内容（新出场角色、新事件、新转折、推断出的走向）逐条标「拟」，另列一份“这些是我生成的”清单一起展示，请用户审核（修改 / 继续）。用户只给了梗概时，也可以先把两三个关键走向用提问工具摆出来让用户选，再立纲——审核越前置，返工越少。用户点头的是“骨架 + 拟项清单”，之后写正文不再继续自由发挥剧情级内容。

**容量核对**（生成骨架时必做）：

- 节拍字数之和应落在 AGENTS.md"每章字数"范围内，且本章覆盖的剧情不超出卷纲分给本章的位置——超范围是抢跑，把后面章的剧情压没了。
- 明显装不下：不要压缩节拍硬塞进一章。告诉用户"这段剧情按节拍走预计要 N 章"，给选择：拆成 N 章分别立纲（先写第一章）；或用户明确要压缩，才缩成一章并说清砍掉了什么。即使用户说"写一章"也一样——"一章"是文件数不是剧情额度，装不下先说再写。
- 明显撑不满：提示"这段撑不满一章"，建议并入相邻剧情或等用户补方向，不靠注水凑字数。

#### 3. 写完整章节

动笔前必读 `novel-craft/SKILL.md` 及对应的 `references/styles.md`、`references/anti-ai.md`。按已审核骨架写正文、控制字数：
- **排版铁律**：严格执行 `AGENTS.md` 正文格式（默认**段首两个全角空格 `　　` + 段间空一行**，绝不允许既不缩进也不空行的密排墙）；自然段以 2–5 句（60–150 字）为主，把同一焦点的连贯动作与观察合在一段，**严禁每句换行的“一句一行”碎段体**。
- **叙事铁律**：活在当下这一秒，用角色实时的动作链、具体感官与对话推进场景；**严禁插播大段回忆总结（“这事本是……那日……后来……那时……”）、严禁段尾甩对偶判词/伪金句、严禁破折号补刀解释、严禁排排坐点名**。
- **创作边界**：正文只落实已审核的骨架。行文所需的感官、动作、过渡可自由写，但写到一半发现需要骨架外的新人物/新事件/新设定才能圆下去时，停下来用提问工具把方案摆给用户拍板，不在正文里先斩后奏。

#### 4. 自检

后台运行 `novel.py lint`（不展示命令），并做人工复检：
1. **格式与碎段修复**：lint 报出的硬错误、「“一句一行”碎段倾向」、「破折号过多」必须当场改掉（把零碎单句段合并为饱满自然段，补齐缩进与空行，删掉句尾解释型破折号）。
2. **去 AI 味清洗**：检查是否有旁白总结代戏、段末金句判词（“X没等来，等来了Y”“没有A，也没有B”）、换壳死比喻（“像一盏将熄的灯”“像个破风箱”）或口号式台词，发现即重写为具体动作与对话。
3. **一致性与越权检查**：连续性（读上章末尾对比）、硬规则（扫描 `AGENTS.md` 关键词）、章纲覆盖（各节拍都落成具体场景，没有压成梗概）、越权检查（正文冒出的新专名/新事件/新设定是否在骨架与拟项清单内，不在的列出请用户决定去留）。

展示结果摘要："自检：字数 ✓ 格式 ✓ 衔接 ✓ 硬规则 ✓ 覆盖 ✓ AI 味 1.2/千字"

#### 5. Memory 自动提取

定稿前，agent 扫描正文提取 memory 更新建议：
- 实力变化（"突破到""晋升""达到xx"等，按本书体系类设定的词汇）
- 物品流转（"得到""交给""夺取"）
- 地点变化（"来到""抵达""离开"）
- 信息获得（"得知""发现""听说"）→ 更新"已知秘密"
- 伏笔推进（按 threads.md 每条的"检索钩子"检测本章是否提及）
- 生成摘要（事件/类型/场景/新信息/出场/状态变化）

展示给用户确认："检测到以下变化，同步到 memory？[state 2 处更新 / threads 推进 T003 / timeline 1 条 / 摘要已生成]"

#### 6. 保存与定稿

保存到 `chapters/volNN/NNNN-章名.txt` → 生成报告 → 问用户"定稿/修改"。

用户确认定稿后，批量更新 memory/（7 个地方，见 novel-core 规程），追加 state 历史快照，不需要用户手动编辑任何 markdown。项目在 git 仓库内时自动 `git add -A` 暂存本次变更，然后问"要提交吗"（提交必问，暂存自动；见 novel-core/AUTOMATION.md「Git 版本管理」）。

## 互动模式（剧情扮演）

用户指定互动（"互动写第 N 章""陪我写"等）、模式选择时选了互动，或快速模式里用户选了修改但只改一处时，切到互动。这个模式里 agent 和用户像在玩剧情推进游戏：agent 写场景，用户选走向。

详细流程见 `references/interactive.md`。简要版：

1. **初始化**：读上下文同"快速模式"第 0-1 步，生成章纲后征求确认。
2. **场景循环**：
   - Agent 写 300–800 字场景到一个决策点
   - 设计 2–4 个选项（顺势/反转/埋伏笔），描述里写预览
   - 用户选择或自由输入
   - Agent 根据选择继续写，再停
3. **控制指令**：继续（自动走顺势）/ 快进到 xxx / 重写上一段 / 回退 / 收尾 / 你来写完
4. **确认与同步**：全章写完后，同样走"自检 → Memory 提取 → 定稿"流程

红线：选项没被选中的走向不进正文；每段只落实用户选定的方向加行文细节，不夹带没被选过的新要素。**所有自主生成的走向、选项一律用提问工具与用户商讨**（没有工具的环境用文字选项兜底）；写着发现非加不可的要素，把它做成下一个选项，不自己拍板。

## 写番外

用户说"写个番外""在第 N 章后加个番外""写个楔子"时用这个。番外不占主线章号，锚在 `NNNNx`（x=a-z），命名与格式约定见 novel-core。

1. **取位**：后台运行 `novel.py insert N --extra`（N=0 是正文前的楔子/序章位），拿到空闲番外位如 `0019c` 和建议路径。锚点已有番外时会一并列出。
2. **写作**：流程同快速模式（读上下文 → 骨架确认 → 写正文 → 自检），但首行写"番外N 章名"或"楔子/序章/外篇 章名"，不写"第N章"。字数可按用户要求短于正文标准。
3. **保存**：写到建议路径（与锚章同卷目录；卷末番外归上一卷）。
4. **定稿同步**：与正章相同的 memory 提取，但 summaries 节名用 `## NNNNx`；timeline 按**故事内时间**落位（番外常写过去或支线，不一定是当前时间点）；state.md"截至"不推进到番外，仍以最新主线章为准。

## 改稿

用户说"改一下第 N 章的 xxx""把 yyy 改成 zzz"，读现有章文件，应用改动，重新检查，保存。

- 只做用户指定的改动，不顺手“优化”别的剧情、人物或设定；发现别的问题报告即可。
- 局部改动（一两句、一段）：直接改，再跑 lint，问定稿。
- 大改（改半章以上）：明确告诉用户会改哪些地方，让他确认再动手。
- 改动涉及关键信息（地名、境界、人物能力）：检查是否与 lore 一致，是否会与其它章节矛盾。
- 改完后重新提取 memory 更新，只同步变化的部分。

## 其他操作

- **查看章骨架**："给我看下第 N 章的大纲" → 读 outline/chapters/NNNN.md 展示。
- **查看章进度**："第 N 章写到哪了" → 检查 chapters/ 是否有该文件，有就展示已写字数，没有就说"还未开始"。
- **补写**："第 N 章太短了""把 xxx 段展开写" → 读现有文件、定位要补的地方、写补充段落、合并、检查流畅性、问定稿。
- **删段**：不建议。改成"这段改成一句过渡"会更好。

## 批量操作

**写多章**："写接下来 3 章"
- 读卷纲 → 生成第 N、N+1、N+2 章的骨架（代拟部分标「拟」）→ 展示确认
- 用户确认后：逐章写作（后章能读前章正文）、每章写完自检
- 全部完成后统一展示，用户说"都定稿"→ 批量同步 memory

## 写作时注意

- **读正文写好的部分**：哪怕修改一章，也要读上一章末尾（至少 1500 字）和相关的下一章起头，保证衔接顺畅。
- **memory 是来源**：memory/state.md 里"已知秘密"决定了角色能做什么。写前查一遍，不要让主角用他不知道的信息行动。
- **字数对标**：AGENTS.md 里的"每章字数"范围是标准，没设时按 2000–3000 执行。超出太多优先拆章——在场景分界处截成两章、各占一章号并补过渡句，舍不得拆才删水；太少先查有没有节拍被略过写薄，再考虑补场景或对话。
- **剧情不许缩水**：章纲每个节拍都要落到正文。最忌讳"本章结尾三句梗概把下两章剧情讲完"——发现就展开写，或把进度停回章纲位置。
- **硬规则**：逐条看一遍 AGENTS.md「硬规则」和「规则」节注入的规则，以及该卷的特殊约束，写的时候脑子里装着。
- **用户原话不落字面**：用户给的想法、台词按本书文风润色后用，不偏离原意和关键词语；用户明确要求原文写入的除外（见 novel-core「输入润色」）。
- **伏笔**：memory/threads.md 的"进行中"条目，本章该埋的埋上、该推进的推进。检查"不可违反"约束。
- **后台工具调用**：所有 `novel.py` 调用在后台执行，不展示命令给用户，只展示结果摘要。

## 说不动时

用户卡住了，或者说"这章不知道怎么写""后半章怎么连接到下一卷"时：

1. 读章纲、卷纲、上一章、下一章卷纲。
2. 用提问工具给两三个剧情走向的选项，各写一句"如果这样做，后面可能..."。
3. 不要替用户做决定；让用户选一个方向。

或者干脆切到互动模式，用"扮演"的方式逐步发展情节。
